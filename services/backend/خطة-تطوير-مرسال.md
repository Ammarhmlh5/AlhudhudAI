# خطة تطوير منصة الهدهد (Go Backend)
## لتكون إحدى منصات الإرسال المتصلة بتطبيق هدهد موبايل

**المشروع:** `github.com/al-hudhud/backend` (Go 1.26.2)  
**التاريخ:** 9 يوليو 2026  
**الرؤية:** منصة الهدهد تصبح واحدة من عدة منصات يمكن ربطها بتطبيق الهاتف

## 1. المفهوم الجديد — Multi-Platform Gateway

```
تطبيق هدهد موبايل (Universal SMS Gateway)
  │
  │  المستخدم يضيف منصات من الإعدادات:
  │
  ├── [منصة الهدهد] ← Go Backend
  ├── [مرسال Excel] ← Supabase Edge Functions
  ├── [منصة أخرى 1] ← أي API
  └── [منصة أخرى 2] ← أي API
```

كل منصة تحتاج:
1. تسجيل الدخول من التطبيق إليها
2. إعطاء التطبيق device_id + push_token
3. استقبال أوامر الإرسال ← التطبيق ينفذها

## 2. المصادقة — التحقق من Supabase JWT

لتمكين منصة الهدهد من قبول توكنات من أنظمة مصادقة مختلفة (كل منصة لها نظامها).

### Middleware جديد: `internal/middleware/multi_auth.go`

```go
package middleware

// MultiAuthMiddleware يقبل JWT من عدة مزودين
// SUPABASE, HUDHUD_JWT, CUSTOM_API_KEY
func MultiAuthMiddleware(providers ...AuthProvider) gin.HandlerFunc {
    return func(c *gin.Context) {
        for _, p := range providers {
            claims, err := p.Validate(c.Request)
            if err == nil {
                c.Set("auth_provider", p.Name())
                c.Set("user_id", claims.UserID)
                c.Set("device_id", claims.DeviceID)
                c.Next()
                return
            }
        }
        c.JSON(http.StatusUnauthorized, gin.H{"error": "No valid auth"})
        c.Abort()
    }
}
```

مكتبة `github.com/golang-jwt/jwt/v5` موجودة بالفعل في `go.mod` — لا حاجة لإضافات.

## 3. تسجيل الأجهزة — Device Registration API

هذا هو **أهم تغيير**: التطبيق يسجل نفسه لدى المنصة (أي منصة) بعد مصادقة المستخدم.

### 3.1 Endpoint جديد: `POST /api/v1/devices/register`

```
Request:

  "device_name": "Samsung S25 Ultra",
  "platform": "android",          // android | ios

  "push_token": "ExpoPushToken[xxxxxxxx]",

Response:
{
  "device_id": "uuid",
  "device_key": "sk_xxxxxxxx", // مفتاح خاص للجهاز
```

## 4. جدول الأحداث الموحد — Unified Events Queue

المنصة تدفع الأحداث إلى هذا الجدول، والتطبيق يسحبها أو يستقبلها عبر WebSocket.

```sql
CREATE TABLE device_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  device_id UUID REFERENCES devices(id) ON DELETE CASCADE,
  type TEXT NOT NULL,          -- send_sms | send_otp | status_report
  payload JSONB NOT NULL,      -- { to, message, sender_name, ... }
  status TEXT DEFAULT 'pending',
    -- pending | processing | delivered | failed
  priority INT DEFAULT 0,
  error TEXT,
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now()
);

CREATE INDEX idx_device_events_pending
  ON device_events(device_id, status, priority DESC, created_at ASC)
  WHERE status = 'pending';
```

## 7. Commission Tracking — تتبع العمولات

### 7.1 الجدول الجديد: `platform_commissions`

```sql
CREATE TABLE platform_commissions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  platform_id UUID NOT NULL,            -- المنصة التي تدفع العمولة
  device_id UUID REFERENCES devices(id),
  event_id UUID REFERENCES device_events(id),
  message_count INT NOT NULL DEFAULT 1,
  commission_rate NUMERIC(10,6) NOT NULL DEFAULT 0.01,  -- 0.01$
  total_commission NUMERIC(12,4) NOT NULL,
  currency TEXT DEFAULT 'USD',
  status TEXT DEFAULT 'pending',        -- pending | billed | paid | void
  billing_period DATE,                  -- الشهر المستحق عنه
  created_at TIMESTAMPTZ DEFAULT now(),
  paid_at TIMESTAMPTZ
);

CREATE INDEX idx_commissions_platform ON platform_commissions(platform_id, status);
CREATE INDEX idx_commissions_period ON platform_commissions(billing_period);
```

### 7.2 آلية الاحتساب

```
عند كل حدث send_sms يتم تسليمه:
  1. حساب commission = عدد الرسائل × 0.01$
  2. تسجيل في platform_commissions (status: pending)
  3. في نهاية الشهر: تجميع commissions → فاتورة للمنصة
  4. بعد الدفع: تحديث status → paid
```

### 7.3 Endpoint جديد: `GET /api/v1/platforms/{id}/commissions`

للمنصة لترصيد عمولاتها (لافتتاح فواتيرها الشهرية).

## 8. ربط الهوية عبر المنصات — User Identity Linking

### 8.1 المشكلة

مستخدم واحد قد يكون له حسابات في منصات متعددة:
- `user@hudhud.com` في منصة الهدهد
- `user@gmail.com` في Supabase (مرسل Excel)
- `device-abc-123` في تطبيق الموبايل

### 8.2 الجدول الجديد: `user_links`

```sql
CREATE TABLE user_links (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  local_user_id UUID NOT NULL,                      -- المستخدم في هذه المنصة
  external_platform TEXT NOT NULL,                   -- 'mursal' | 'mobile' | 'other_platform'
  external_user_id TEXT NOT NULL,                    -- user_id في المنصة الأخرى
  external_email TEXT,
  linked_via TEXT DEFAULT 'manual',                  -- manual | auth | device_registration
  is_verified BOOLEAN DEFAULT false,
  linked_at TIMESTAMPTZ DEFAULT now(),
  UNIQUE(local_user_id, external_platform)
);
```

### 8.3 تدفق الربط

```
1. المستخدم يسجل الدخول إلى منصة جديدة من تطبيق الموبايل
2. التطبيق يرسل للتطبيق: "هذا جهازي (device_id)" مع توكن المنصة الجديدة
3. المنصة تستعلم: هل device_id مرتبط بمستخدم آخر؟
   - لا: تربط device_id بالمستخدم الحالي
   - نعم: تسأل المستخدم "هل تريد دمج الحسابات؟"
4. إنشاء user_link بين local_user_id و external_user_id
```

## 9. Events API Contract — عقد JSON الموسع

### 9.1 حدث `send_sms` — المواصفات الكاملة

```json
{
  "event": {
    "id": "evt_uuid_v4",
    "type": "send_sms",
    "version": "1.0",
    "platform_id": "platform_uuid",
    "campaign_id": "camp_uuid_optional",
    "batch_id": "batch_uuid_for_grouping",
    "priority": 0,
    "schedule_at": "2026-07-10T14:00:00Z",
    "ttl_seconds": 86400,
    "max_retries": 3,
    "payload": {
      "to": "+9677xxxxxxx",
      "message": "نص الرسالة (أقصى 160 حرف)",
      "sender_name": "هدهد",              // اسم المرسل (اختياري)
      "is_unicode": true,
      "message_parts": 1,
      "platform_fee": 0.01,              // العمولة على هذه الرسالة
      "reference_id": "client_ref_123"   // مرجع المنصة
    }
  },
  "metadata": {
    "platform_name": "منصة الهدهد",
    "auth_provider": "hudhud_jwt",
    "submitted_at": "2026-07-09T12:00:00Z"
  }
}
```

### 9.2 أنواع الأحداث

| type | الوصف |
|------|-------|
| `send_sms` | إرسال رسالة SMS |
| `send_otp` | إرسال كود تحقق (أولوية عالية) |
| `cancel_campaign` | إلغاء حملة إرسال سابقة |
| `status_report` | طلب تقرير حالة رسالة |
| `ping` | اختبار اتصال ← pong |

### 9.3 أكواد الحالة

| status | الوصف |
|--------|-------|
| `pending` | تم إنشاء الحدث، لم يُستلم بعد |
| `picked_up` | التطبيق استلم الحدث |
| `processing` | التطبيق بدأ الإرسال |
| `partially_delivered` | جزء من الرسائل تم توصيله |
| `delivered` | تم التوصيل بنجاح |
| `failed` | فشل التوصيل |
| `expired` | انتهت صلاحية الحدث (TTL) |
| `cancelled` | ألغي بواسطة المنصة |

## 10. Error Handling & Retry — معالجة الأخطاء وإعادة المحاولة

### 10.1 Dead Letter Queue

```sql
ALTER TABLE device_events ADD COLUMN retry_count INT DEFAULT 0;
ALTER TABLE device_events ADD COLUMN max_retries INT DEFAULT 3;
ALTER TABLE device_events ADD COLUMN last_error TEXT;
ALTER TABLE device_events ADD COLUMN next_retry_at TIMESTAMPTZ;

CREATE TABLE dead_letter_queue (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  original_event_id UUID REFERENCES device_events(id),
  device_id UUID REFERENCES devices(id),
  type TEXT,
  payload JSONB,
  error TEXT,
  failed_at TIMESTAMPTZ DEFAULT now(),
  resolved BOOLEAN DEFAULT false
);
```

### 10.2 استراتيجية Retry

```
محاولة 1 → فشل → انتظار 30 ث → محاولة 2 → فشل → انتظار 5 د → محاولة 3 → فشل → DLQ
                              ↕
                         إذا الخطأ "جهاز غير متصل":
                         التطبيق يخطر عبر Push Notification بدلاً من REST
```

### 10.3 Fallback بين SIM و API

```
1. المحاولة الأولى: عبر القناة الافتراضية (حسب priority)
2. إذا فشلت: التبديل إلى القناة الأخرى
3. إذا فشلت كل القنوات: تسجيل في DLQ + إشعار للمنصة
```

## 11. Notification Flow — تدفق الإشعارات الكامل

### 11.1 WebSocket Events Enhancement (تعديل `internal/ws/hub.go`)

```
حدث WebSocket جديد: type = "SEND_SMS"
{
  "type": "SEND_SMS",
  "event_id": "evt_uuid",
  "payload": { "to": "...", "message": "..." },
  "timestamp": "2026-07-09T12:00:00Z"
}
```

### 11.2 Push Notification Integration

```
عند انقطاع WebSocket:
  1. المنصة ترسل Push Notification عبر Expo Push API
  2. تستخدم push_token المخزن في جدول devices
  3. التطبيق يستلم الإشعار ← يفتح التطبيق ← يسحب الحدث عبر REST
```

### 11.3 التدفق الكامل

```
1. [منصة] تدفع حدث إلى device_events (status: pending)
2. [منصة] ← WebSocket → [تطبيق] ← إذا متصل (فوري)
    أو
   [منصة] ← Expo Push API → [تطبيق] ← إذا غير متصل
    أو
   [منصة] ← REST Fallback → [تطبيق يسحب كل N ثانية]
3. [تطبيق] يستلم الحدث ← يبدأ المعالجة ← يحدّث status (processing)
4. [تطبيق] ← POST status → [منصة] ← بعد الإرسال
5. [منصة] تحفظ status ← تحدث Dashboard
6. [منصة] تسجل commission في platform_commissions
```

### 11.4 Expo Push Notification Sender

```go
// internal/notifications/expo.go
package notifications

type ExpoPushSender struct {
  // يرسل Push Notification عبر Expo Push API
  // https://exp.host/--/api/v2/push/send
}
```

يُستخدم عند إنشاء حدث جديد والجهاز غير متصل عبر WebSocket.

## 12. تدفق تحويل منصة الهدهد ويب ← مرسل Excel

### 12.1 السيناريو

```
1. المستخدم في منصة الهدهد ويب (hudhud.com)
2. يضغط "إرسال عبر Excel" ← تحويل إلى مرسل Excel
3. مرسل Excel يعرض واجهة رفع Excel
4. بعد الرفع والإرسال ← النتائج تظهر في تطبيق الموبايل
```

### 12.2 آلية التحويل مع JWT Context

```
1. منصة الهدهد تولّد JWT يحتوي:
   {
     "sub": "hudhud_user_id",
     "email": "user@hudhud.com",
     "redirect_to": "https://mursal.hloov.com",
     "device_id": "known_device_uuid",
     "iat": ...,
     "exp": ... + 5 دقائق
   }

2. التوجيه إلى: https://mursal.hloov.com/?token=<JWT>

3. مرسل Excel يستقبل JWT ← يتأكد من توقيعه (JWKS)
   - يستخرج user_id ← ينشئ حساب أو يربط
   - ينشئ user_link بين hudhud_user_id و supabase_user_id

4. المستخدم يرفع Excel ويُرسل كالمعتاد

5. حملة الإرسال مرتبطة بـ device_id ← الموبايل يستقبل التحديثات
```

### 12.3 JWKS Endpoint في منصة الهدهد

```
GET https://api.hudhud.com/.well-known/jwks.json
{
  "keys": [
    {
      "kty": "RSA",
      "kid": "hudhud-main-2026",
      "n": "...",
      "e": "AQAB"
    }
  ]
}
```

يستخدمها مرسل Excel للتحقق من JWT الصادر من منصة الهدهد.

## 14. ملاحظات

1. **Platform-agnostic**: الـ API أعلاه لا يعتمد على Hudhud — أي منصة تقدر تستخدم نفس الـ pattern
2. **WebSocket اختياري**: التطبيق يقدر يستخدم Polling (GET events) أو WebSocket — حسب ما تدعمه المنصة
3. **Device Key**: كل جهاز ياخذ مفتاح سري يستخدمه لاحقاً للمصادقة (بدون الحاجة لتسجيل دخول كامل في كل مرة)
4. **Commission**: 0.01$ لكل رسالة — مسجلة في جدول منفصل للفواتير الشهرية
5. **JWKS**: كل منصة تصدر مفتاح عام للتحقق من JWT — لا استعلامات API بين المنصات
